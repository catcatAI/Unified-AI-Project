## 研究與精進（L1-3/L1-6，不立即重訓）

### 為何不立即重訓

- **硬體**：本機 15.5GB RAM + **Intel Arc B570 10GB**（device ID 8086:e20c, glxinfo 10172MB, Mesa BMG G21, `/dev/dri/renderD128`），`lspci` 曾無 `arc` 字符串（Device e20c）已修為 device ID 映射 + Video memory 精確；`GARDEN SNN` 7.6s/次已顯 CPU 瓶頸（Arc 無 CUDA，torch 走 CPU），100K 訓練若全量載入 + SNN 矩陣 `V²×4B`（10K→0.38GB, spec-driven 自適應 35000→0.47GB）易 OOM 但 15.5GB 仍可控。
- **數據**：100K 已生成，但訓練需 `train_pipeline.py` 的 `learn_batch` 逐批 Hebbian 更新；若 batch=500、10K vocab，單批 ~5ms，100K → 200 批 → ~1s，但舊 GARDEN 曾因 `[V,V]` dense 導致 >10GB（`garden_snn.max_vocab 10K` 已為 lean 檔位）。
- **精進優先**：應先研究「為何 deep_chain 50 跳為 0」（`propagation_hops=3` 限制）與「改述召回 11% 的瓶頸是 threshold 還是負樣本」，再決定加量策略，避免「算力消耗造成誤以為沒法達成」。

### L1-3 探針結果

`scripts/probe_snn_recall.py`（8 樣本，0.62s，int8 ONNX）在**注入訓練集**時 100% 召回（樂觀）；`INTELLIGENCE_ASSESSMENT` 的 11% 是**未見改述**上的真實 SNN-ONLY 召回。差距說明需 **泛化而非記憶**。

**精進方案（分批+資源保護）**：

1. **FixedSizeCore slots 65536→131072**：`compute_int("unified","slots")` 已支持 128K，但需 `mmap` 或分片載入避免 259MB→518MB 一次性峰值。
2. **負樣本挖掘**：`semantic_qa` 改為「同 topic 正樣本 + 隨機負樣本」對比訓練，batch 32，lr 1e-4，每 epoch sleep 0.1s。
3. **閾值自適應**：`threshold_value("semantic_qa.threshold")` 已可硬體感知（`laptop_power_saver`→0.70 提升召回，`high_performance`→0.78 提升精確）。
