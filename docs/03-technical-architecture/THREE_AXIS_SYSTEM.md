# 三軸系統 (Three-Axis System) — 上下文上限、組成與引擎取代分析

> 本文件分析三軸系統的理論架構、上下文組成與長度上限，並逐一檢視現有
> **確定性引擎 / ED3N 引擎 / GARDEN 引擎**如何被三軸系統及其衍生引擎取代。
> 這是**分析與設計**層級的文件。三軸系統目前為概念驗證階段（
> `scripts/` 與 `/tmp/opencode/verify_*.py` 有數學域實驗），尚未整合進產品。

## 1. 三軸系統的定義

三軸系統把「內容」與「結構」分離為兩個正交軸，第三軸是二者的橋樑：

| 軸 | 內容 | 範例（`3+5=8`） |
|---|---|---|
| **UTF-8 軸** | 內容的固定數值編碼 | `'3'=51`、`'+'=43`、`'5'=53`、`'='=61`、`'8'=56` |
| **位置軸** | 內容在序列中的下標 | 位置 0→`'3'`、1→`'+'`、2→`'5'`、3→`'='`、4→`'8'` |
| **內容軸** | 位置所容許的內容值分布 | 位置 4 傾向結果（小數字），位置 0/2 傾向操作數 |

> ⚠️ **核心原則（2026-08-19 確立）**：**UTF-8 數值是「編碼」，不是「數學」**。
> `'1'=49`、`'2'=50`、`'3'=51` — 但 **49+50 ≠ 51**（那是 `'c'`）。編碼值只代表
> 各自對應的字符，**同軸之間不能做算術運算**。因此內容軸/位置軸的「計算」
> 本質是**分類、分組、統計召回**，**不是**對編碼值做 α·a+β 的數值變換。早期
> 概念驗證的最小二乘（§1 下方）已被 §6 線性陷阱實驗證實為「線性擬合×線性
> 數據」的數學必然，且數學上不該對編碼值做算術。已實作引擎（§8）採用**純統計
> 召回 + 學習錨點對位**，符合本原則。

核心機制（依概念驗證實驗 `/tmp/opencode/verify_learned_matrix.py`）：

```
訓練: 語料逐字符 → UTF-8 數值 → 按 (位置1操作符, 位置2右操作數) 分組
      → 最小二乘 (XᵀX)⁻¹Xᵀy 學習「位置0 數值 → 位置4 數值」關聯係數 (α, β)
對話: 新輸入 → UTF-8 數值 → 查學到的 (α, β) → 計算 c = α·a + β → 還原字符
```

> ⚠️ **注意**：上列「最小二乘 α·a+β」是**早期概念驗證的過時機制**。依上方核心
> 原則，對**編碼值**做 α·a+β 是數學上不成立的（`49+50=99='c'` 而非 `51='3'`），
> 且已被線性陷阱實驗證實無法泛化。**已實作引擎不用最小二乘** — 改為 §8 的
> **編碼值分組/統計召回 + 學習錨點對位**。

**概念驗證結果**（0~9 四則運算，184 全組合 / 92 訓練 / 92 測試）：

| 訓練覆蓋 | 正確率 | 機制 |
|---|---|---|
| ≥2 點（學到斜率） | **63/63 = 100%** | 矩陣對未見過的 `a` 也能算 |
| 1 點（α 退化 0） | 0/15 | 單點學不出斜率，只回常數 |
| 未覆蓋 (op,b) 組 | 0/14 | 訓練無該組合，資訊不存在 |

> ⚠️ **誠實註記（2026-08-18 複查）**：四則 100% **不是「矩陣學會泛化」的證據**。
> 複查實驗（`/tmp/opencode/verify_linearity_trap.py`）證明：同一矩陣+最小二乘，
> 對線性真值（四則，固定 b 後 c=α·a+β）殘差必為 0，100% 是「線性擬合 × 線性數據」
> 的**數學必然**；換成非線性真值（`c=a² mod 10`）同一架構崩潰到 **10%**。
> 因此四則實驗只能證明「三軸能承載線性可擬合的數值關係」，
> **不能**推論三軸對真實語料（非線性、多字節、可變長）有效。取代引擎的分析是
> 「概念可行」而非「已驗證」。

矩陣**自動發現**的四則定律（無手刻規則）——但注意這是線性必然（見上方誠實註記）：

```
'+' b=1: α=1.0 β=+1   → c = a + 1    （即「a+1」）
'*' b=2: α=2.0 β=-48  → c = 2a - 48  （即「a×2」）
'/' b=2: α=0.5 β=+24  → c = a/2 + 24 （即「a÷2」）
'-' b=3: α=1.0 β=-3   → c = a - 3    （即「a−3」）
```

## 2. 上下文組成 (Context Composition)

三軸系統的「上下文」由三個正交來源組合而成：

### 2.1 內容層（UTF-8 軸）

- **即時內容**：當前輸入的逐字符 UTF-8 數值序列。
- **環境內容**：與輸入共同出現的內容值統計（位置×內容矩陣的列分布）。
- 本質上是**內容位址化**（content-addressed），與現有 `DictionaryLayer` 的
  `c1/c2...` key 機制同源，但以 UTF-8 數值取代任意分配的 token ID，因此
  **無 OOV、無 `grow()` 依賴**（未見過的字符也有固定數值）。

### 2.2 結構層（位置軸）

- **位置** = 字符串下標（位置 0..n）。位置攜帶**順序**與**間距**資訊。
- **關聯** = 位置與位置的關係（`=` 兩側、操作符與操作數、鄰居對）。
- 概念驗證證明：**位置由關聯讀出，不由內容值算出**。
  證據：`5` 單值同時是操作數與結果（多對多）；`(5, '+', '=')` 才唯一確定
  「右操作數」。因此位置軸必須存「內容×內容」的關聯結構，而非「內容→位置」的函數。

### 2.3 學習層（分組/召回統計）

- 從訓練語料學出的「位置 i → 位置 j」**值對分組統計**（同一 (α,β) 分組鍵下的
  出現分布），非數值變換函數。
- 這是「結構的記憶」：**不是對編碼值做算術**，而是對編碼值做**分組、計數、
  召回**（見 §1 核心原則 — 編碼不可計算）。

### 2.4 上下文的實際組成範例

```
輸入: "8*1=?"  （? 為待還原位置）
UTF-8: [56, 42, 49, 61, None]        （逐字符 UTF-8 位元組；'8'=56 '*'=42 '1'=49 '='=61）
位置:  [0,   1,  2,  3,   4]
已知關聯: (pos1=42='*', pos2=49='1') → 分組鍵
召回: 訓練中該分組鍵下位置 4 出現過 56='8'（分組統計，非 α·a+β 計算）
還原: "8*1=8"
```

## 3. 上下文上限 (Context Bounds)

三軸系統的上限由三個獨立的維度決定，**互不衝突**，皆可獨立配置：

### 3.1 位置軸上限 = 序列最大長度（`MAX_SEQ_LEN`）

- 上下文長度 = 可容納的最大位置數。
- 概念驗證用長度 5（`a op b = r`）；實際對話需要長度對齊現有歷史上限。
- **對齊現況**：對話 session 綁定最後 80 條訊息（=40 輪，
  `api/routes/chat_routes.py:1464`）；prompt 取最後 10 條
  （`prompt_builder.py:539`）。
- 三軸系統的序列長度上限應**分層**：
  - 單句層：最大句長（例如 200 字符）
  - 對話層：最後 N 句的連接（例如 40 輪 × 平均句長）
- **記憶代價**：位置×內容矩陣隨 `MAX_SEQ_LEN` **線性**增長（位置列數 × 256）；
  但關聯鍵若採「位置對」則 **O(MAX_SEQ_LEN²)**（見 §3.3）——長上下文下
  關聯維度才是主導，非位置矩陣本身。

### 3.2 內容軸上限 = UTF-8 基數（256）

- UTF-8 單字節有 256 個固定值。這是最小表徵。
- **CJK 走逐位元組**（`中`=[228,184,173]）— 每個位元組都是 0..255 的內容軸值，
  內容軸維持 256 基數；CJK 字符佔用 3 個位置（已實作，§8）。
- **與現有上限對比**：

| 現有系統 | 上限 | 三軸系統對應 |
|---|---|---|
| GARDEN dictionary `max_entries` | 10000（conservative）/ 51812（extended） | 256（UTF-8 單字節）或 CJK 擴展 |
| GARDEN SNN `max_vocab` | 51812（RAM clamp） | 位置數 × 內容值 |
| ED3N dictionary `max_entries` | 500000 | 256 |
| 模板層 `_templates_cap` | 500 | 由分組統計取代（不存模板字串） |

**三軸系統的內容軸上限遠小於現有系統**（256 vs 10000+），因 UTF-8 是
**固定、封閉、無需增長**的基數。這是它的根本優勢：**無 `grow()`、無 prune、
無 OOV、無 vocabulary 膨脹**。

### 3.3 關聯軸（分組鍵的規模）

- 關聯係數按「分組鍵」存。概念驗證的分組鍵 = (位置1的值, 位置2的值)，
  是**值對**（operator × operand）。
- 值對鍵數上限 = 值域 × 值域 = 256 × 256 = **65,536**（內容軸 256 時）。
- 若關聯定義擴展為**位置對**（位置 i 與位置 j 的關係），鍵數升為
  **O(MAX_SEQ_LEN²)** —— 例如 40 輪 × 每輪 200 字符 = 8,000 位置時，
  位置對 ≈ 3,200 萬，這才是真正的容量瓶頸。
- **訓練需求**：每個鍵需要 ≥2 個樣本才能學出非退化斜率（概念驗證：
  單點組 α=0）。因此訓練需求 = 鍵數 × 2，這是「資料需求」，不是儲存上限。

### 3.4 上下文上限的定義（修正）

**上下文上限 = 位置軸容量 `MAX_SEQ_LEN`**，即三軸能處理的 UTF-8 位元組序列長度
（一個 CJK 字符 = 3 個位元組 = 3 個位置）。

```
上下文上限 = MAX_SEQ_LEN ≥ 對話歷史總位元組數
            = 最後 40 輪 × 每輪平均位元組數
儲存（位置×內容矩陣） = MAX_SEQ_LEN × 內容值域 (256)
關聯鍵數 = 值域² (值對)   或    MAX_SEQ_LEN² (位置對)
訓練需求 = 關聯鍵數 × 每鍵 ≥2 樣本
```

> ⚠️ **修正說明（2026-08-18 複查）**：先前版本把三個獨立性質相乘
> `MAX_SEQ_LEN × 256 × Σ(每組樣本≥2)` —— **這是錯的**。三者不是乘數關係：
> `MAX_SEQ_LEN` 決定**能放多長**（上下文長度）、`256` 決定**每格能放什麼值**
> （解析度）、「每鍵 ≥2 樣本」決定**訓練需求**（非容量）。上下文上限就是
> `MAX_SEQ_LEN`，由對話歷史長度決定，而非三者相乘。原公式也無實際數值。

對比現有 LLM 上下文：**無全域 token 預算**，僅「條數上限 + 每條 150-500
字元截斷」（`prompt_builder.py:549,593-596`）；輸出 `max_tokens` 預設 256-512。
三軸系統的上限是**結構化的、可預測的**，不是截斷式的。

### 3.5 2GB 記憶體下的實際上限（計算）

以 **2GiB** 為預算，float32 儲存，逐方案計算（2026-08-18）：

| 方案 | 記憶體模型 | MAX_SEQ_LEN | 實際代價 |
|---|---|---|---|
| **值對關聯**（概念驗證方式，鍵=(值,值)） | 位置×內容矩陣 `L×256×4B` + 關聯表固定 `65,536×12B≈768KB` | **≈ 2,097,152 字符** | 關聯表不隨 L 增長，記憶體幾乎全留給語料 |
| **位置對關聯**（全量，鍵=(位置,位置)） | 關聯表 `L²/2 × 12B` | **≈ 18,918 字符** | 鍵數 1.79 億；訓練需求 ≈ **3.6 億樣本**（不切實際） |

**相比其他 AI**（1 token ≈ 4 英文字符 / ≈1 中文字符）：

```
三軸-值對關聯:   ~209萬字符 ≈ 52萬英文token / 209萬中文token   ← 超過全部
三軸-位置對:     ~1.9萬字符 ≈ 4,700英文token                    ← 落後全部
Gemini 1.5 Pro:  1,000,000 tokens
Claude 3.7:      200,000 tokens
GPT-4o / Llama3: 128,000 tokens
```

**關鍵結論**：三軸要在記憶體上勝出，關聯必須採**值對**（或稀疏位置對），
不能存全量位置對。值對鍵數上限固定（65,536），記憶體隨語料線性增長 →
2GB 可承載 209 萬字符語料統計，超過 Gemini 1M token。位置對是 O(L²)
——長上下文直接爆記憶體，且訓練資料需求（每鍵 ≥2 樣本）不切實際。
概念驗證選 (op, b) 分組正是值對，這不是巧合。

> ⚠️ **誠實修正（2026-08-19）**：上述「209 萬字符」是**位置×內容矩陣**的理論
> 模型，**不是實作實際達到的數字**。現行引擎在矩陣之外還維護三張擴張表：
> `exact_completions`（每個樣本的**每個前綴**各存一條，上限 1,000,000）、
> `prefix_recall`（有界左文脈，上限 131,072）、`anchor_suffixes`（全後綴，
> O(L²) 式）。實測 42,335 樣本（corpus_bytes=1,825,609，見 §8.2）：
> 訓練期間估測記憶體 **1,486 MiB**、磁碟 checkpoint **948.8 MiB** — 對 1.74 MiB
> 語料的**壓縮比為 0.0012，即記憶體是語料的 853.5 倍（重度擴張，非壓縮）**。
> 「2GB 可承載 209 萬字符」在現行實作下**不成立**；真正可承載約
> 2,148 MiB ÷ 853.5 ≈ **2.5 MiB 語料**（若擴張因子不變）。此擴張的根因是
> 前綴/後綴表按樣本長度累積（CJK 3 位元組/字加倍了前綴數），見 §8.2 的表量。

### 3.6 與位置編碼現況的差距

現有 GARDEN / ED3N **皆無 position encoding**
（全 src 搜尋僅命中中文數字的 "positional multipliers"；
`DETERMINISM_CLASSIFICATION.md:157` 明載「無 next-token 生成、長文建構不在
字典+SNN 可表能力內」）。三軸系統的「位置軸」正是補這個空缺的核心維度。

## 4. 現有引擎取代分析

三軸系統目標：**以「三軸 + 依此的引擎」完整取代現有確定性引擎、ED3N、GARDEN**。
逐一分析可行性與取代方式。

### 4.1 取代現有確定性引擎

**現況**（`garden_engine.py:309-362`）：

| 引擎 | 函數 | 委派 | 類型 |
|---|---|---|---|
| `_try_math` | :309 | `VectorDictionary.route_math` | 算式求值 |
| `_try_logic` | :318 | `evaluate_logic` | 布林 |
| `_try_knowledge` | :329 | `route_knowledge` | 事實查詢 |
| `_try_reasoning` | :340 | `route_reasoning` | 符號推理 |
| `_try_chain_reasoning` | :351 | `relational_chain` | 比較鏈 |

**三軸取代方式**：

| 引擎 | 能否被三軸取代 | 分析 |
|---|---|---|
| **math** | ✅ **完全取代**（概念驗證域） | 四則運算可承載：矩陣從語料學出**值對分組召回**（非 α·a+β 泛化 — 編碼不可計算，見 §1 核心原則）。`route_math` 的三角/log/中文數字是「規則+表」，三軸可用更大的語料組學出或保留為確定性函數 |
| **logic** | ⚠️ 部分 | 布林運算 `and/or/not` 是三值關係，三軸可學 `(左, op, 右) → 結果`。但 XNOR 缺口需語料覆蓋才可學 |
| **knowledge** | ⚠️ 部分 | 事實查詢（顏色/單位/動物腿數）是**查表**，三軸的內容軸可存 `(entity, attr) → value` 關聯，實質是改存位置的查表 |
| **reasoning** | ⚠️ 部分 | 傳遞關係、雞兔同籠是**結構推理**，三軸位置軸可表「誰在誰前面」，但二元線性組求解（`_solve_word_problem`）是演算法，不適合純矩陣 |
| **chain_reasoning** | ⚠️ 部分 | 比較鏈（A>B, B>C → A 最高）是三軸位置軸的理想應用（`[] is taller than []` 就是位置模板），但閉包求解仍是演算法 |

**結論**：三軸可取代確定性引擎中**查表型與線性結構型**（math、簡單 logic、
knowledge、chain 的模板部分）；**演算法型**（雞兔同籠求解、閉包傳遞）應保留
為確定性引擎，三軸負責學結構、引擎負責算。此即「矩陣學結構、函數算結果」的分工。

> **2026-08-19 補充（公式求解器已實作）**：物理領域的「演算法型」缺口
> （F=ma、動能 `½mv²`、`v=at`、動量、功、功率、重量 `F=mg`）已由
> `ai/memory/formula_solver.py` 閉合，並接入 `PhysicsDomainEngine.compute`
> （`domain_ripple.py`）— 解析單位錨點（kg/m/s²/N/J…）+ 問題子句目標偵測，
> 求解單未知文字題。20 測試（`tests/ai/test_formula_solver.py`）。誠實邊界：
> 這是符號演算（確定性引擎、域軸上的值），非「理解物理」。

### 4.2 取代 ED3N 引擎

**現況**（`ed3n_engine.py`）：

- DictionaryLayer（`max_entries=500000`，key `c1/c2...` 內容定址）→ **encode/decode 骨幹**
- CoreNetwork（RelationGroup 分組稀疏網路，BFS 3 hops）→ 關聯激發
- ReflexLayer（LRU 128）→ 短路
- InputEnricher、RelationClassifier、HormonalModulator → 輔助
- `anchored_decode`（`output_anchor.py`）→ 解碼

**三軸取代方式**：

| ED3N 元件 | 三軸對應 | 分析 |
|---|---|---|
| DictionaryLayer | UTF-8 軸（256 基數） | **取代**：內容定址保留，但 key 從 `l1/l2` 改為 UTF-8 數值。無 `grow()`、無 prune、無 OOV、`max_entries` 從 500000 降到 256 |
| CoreNetwork 分組關聯 | 位置軸 × 內容軸關聯矩陣 | **取代**：`classify_pair` 三組關係 = 三軸的「位置與關聯」，學出的是分組統計而非固定分組 |
| ReflexLayer | 位置軸精確匹配 | 取代：位置 0..n 的逐位置匹配即 reflex；UTF-8 定值使匹配確定性 |
| `anchored_decode` | 值對分組召回還原 | **取代**：解碼是「用分組統計查未知位置」，比 anchored_decode 的 top-k 合併更直接 |
| SequenceTrainer / JointTrainer | 分組統計聚合 | **取代**：訓練是「對每組聚合出現分布」，無需多階段 trainer |

**關鍵差異**：ED3N 是「**內容定址 + 神經關聯**」，三軸是「**內容定址 +
位置關聯計算**」。二者共用內容定址哲學，但三軸以**位置**取代**神經脈衝**作為
結構的載體 — 後者無需 threshold、spike、weight decay，完全確定性、可重現。

### 4.3 取代 GARDEN 引擎

**現況**（`garden_engine.py:1073-1230`）：

```
Stage 0 Emotion → Stage 1 Math/Logic/Reasoning → Stage 1.6a Template recall
→ Stage 1.6b Chain → Stage 2 Reflex → Stage 3 Knowledge → Stage 4 Multi-step
→ Stage 5 Encode → Stage 6 SNN forward → Stage 6.5 Anchor calibration
```

**三軸取代方式**：

**關鍵差異**：GARDEN 是「**字典存內容 + SNN 存關聯（權重）+ 模板存結構

## 6. 風險與限制（誠實評估）

1. **線性假設（已實證崩潰，已捨棄）**：早期概念驗證的最小二乘關聯是線性擬合，
   對非線性真值（`a² mod 10`）同一架構從 100% 崩潰到 **10%**
   （`/tmp/opencode/verify_linearity_trap.py`）。加上 §1 核心原則（編碼不可
   計算），**已實作引擎已捨棄最小二乘**，改採純統計召回 — 此風險不適用於
   已實作引擎。**未解問題轉為**：純召回對未覆蓋分組不泛化（見風險 2）。
2. **資料覆蓋依賴**：未覆蓋的分組 0% 正確（誠實「不知道」），不會瞎猜
   — 這是優點也是限制。需語料覆蓋所有需要的分組。
3. **位置軸對齊**：跨實例位置一致性（`[] is taller than []` 的 `[]` 對齊）
   是三軸取代模板層的關鍵。學習錨點對位（§8.5）已驗證固定長度的空白/前置詞/
   長度偏移；可變長與語義變異（`plus` vs `+`）仍需語料覆蓋。
4. **多字節 UTF-8（已實作）**：CJK 以**逐位元組**序列處理（`中`=[228,184,173]），
   位置軸計數位元組而非字符 — 內容軸維持 256 基數、無需擴展。代價是 CJK 佔用
   3 個位置，`max_seq_len` 下可容納的 CJK 字符數約為 ASCII 的 1/3。
5. **取代範圍**：確定性引擎的**演算法型**（雞兔同籠、閉包）不應被矩陣取代
   — 那是把演算法硬塞進矩陣，得不償失。三軸取代「結構」，引擎保留「演算法」。

### 8.1 與概念驗證的差異（誠實）

概念驗證（§1）用**最小二乘關聯係數** `c=α·a+β` 學「位置0→位置4」的線性
映射，被證實是「線性擬合 × 線性數據」的數學必然（§6 線性陷阱）。已實作
引擎**沒有**沿用最小二乘泛化 — 誠實評估已證明它對非線性真值崩潰，不能
宣稱泛化能力。已實作引擎改採**純統計召回**：

| 層 | 內容 | 用途 |
|---|---|---|
| `_position_content` | 位置×內容稀疏矩陣 | 該位置出現過的 UTF-8 值統計 |
| `_transitions` | (左值,右值) bigram | 左鄰預測 |
| `_prefix_recall` | 有界左文脈（≤6 位元組）→ 下一值 | 單步消歧回退 |
| `_exact_completions` | **完整已知前綴 → 下一值** | 對話生成的續接路徑（fallback） |
| `_anchor_problems` | **學習錨點切分後的正規化問題 → 答案** | 對話的主路徑（滑動對位） |
| `_anchor_suffixes` | 正規化問題後綴 → 答案統計 | 前綴不敏感的後綴查找 |

**解析優先序**（`process`）：`anchor-aligned`（學習錨點滑動對位，conf 0.95）
→ 逐字符 `exact-completion` → `prefix-recall` → `position-exact` →
`position-majority` → `bigram` → `global`。

**對話生成**（`generate`）**只在 `exact-completion` 路徑續接**：逐字符把完整
已知前綴查 `_exact_completions`，命中才續接；一旦完整前綴在語料中沒有後續
（= 記憶答案的結尾）就停止。短窗口 `prefix-recall` **不**用於續接 — 實驗
證實它會誤召回歧義後繼（`92=101` 同時屬於 `293 - 192=101` 與
`827 + 192=1019`，產生尾隨垃圾字符），僅作單步回退。

> ⚠️ **誠實註記（更新 2026-08-18）**：對話能力本質是**語料召回**（memorisation），
> **不是泛化**。未見過的問題會退到統計回退，不保證正確。但 **§8.5 的學習錨點
> 滑動對位**已擴展「召回」的範圍：空白變異、前置詞差異（`what is`）、長度
> 偏移都不再需要逐字符一致 — 這是**對位自由度**，不是**數值泛化**（四則的
> 答案仍是查回，非計算）。

### 8.3 記憶體安全

- `_exact_completions` 上限獨立配置（`MAX_EXACT_COMPLETIONS = 1,000,000`，
  約 50MB）— 與值對表（65,536）解耦：它追蹤語料前綴，不是 256² 值對空間。
- `estimate_memory_bytes()` 是**維護式計數器**（學習時增量、修剪時減量），
  避免每次調用全表掃描（早期版本每次 O(N) 重算導致 5000 樣本超時 0.34s→
  修正後 40k 樣本僅 4.1s）。
- 若估算超 cap，`_enforce_memory_cap` 先逐出最舊的 bigram（LRU），從不 OOM。

### 8.4 已知限制

1. **非泛化**：未見問題退統計回退（§8.1 誠實註記）— 滑動對位補「形式」變異，
   不補「內容」泛化。
2. **`max_seq_len` 截斷**：超過 `max_seq_len`（預設 512）的樣本只學前段。
3. **exact_completions LRU**：超大語料（>1M 前綴）逐出最舊前綴，老樣本
   的召回可能丟失 — 是可調的記憶體/召回取捨。
4. **多字節 UTF-8（已實作，2026-08-19）**：CJK 以**逐位元組**值（0..255）處理，
   位置軸計數位元組而非字符（`中` 佔 3 位置）。消歧窗口（`PREFIX_DEPTH=6`）
   是位元組窗口 — CJK 下同等窗口能覆蓋的字符數較少（§6 風險 4）。

### 8.5 學習錨點滑動對位（Learned Anchor Alignment）

> 2026-08-18：位置軸的「滑動對位」自由度以 **EM 式學習**補上，非手寫規則。
> 用戶指出：對位不該寫死（例如硬編「找 `=`」），應是**預設 + 訓練 + 迭代**。

**AnchorLearner（`anchor_learner.py`）EM 循環**：

```
預設錨點(prior) = {= + - * / ? 空白 . , ! ( ) [ ] { } : ;}  ← 僅起點
   ↓ E-step（對齊）: 每樣本找「終端分隔」= 最右側、其右區無其他錨點的錨點
   ↓ M-step（重估）: 對曾當終端分隔的值評分
         score = 0.8×terminality(該值作為分隔的占比) + 0.2×coverage(語料占比)
   ↓ 取 top-K → 新錨點集 → 迭代直到收斂（錨點集不再變）
```

**實證收斂**（40k 真實樣本）：**2 輪收斂** → 錨點集 `{=, -, .}`，
`=` 分數 **0.856** 碾壓（`-` 0.141、`.` 0.062）。資料自己發現 `=` 是答案
分隔符、`-`/`.` 是運算子/小數點 — **非手寫**。

**對位後的查找**：錨點切 `problem | delimiter | answer` → 問題做空白摺疊
（`178  +  101` → `178+101`）→ 建「完整鍵 + 全部後綴」索引。probe 查詢：
完整鍵優先，miss 則從最長後綴走查且**只接受唯一答案**（歧義後綴拒絕，
避免 `101` 同屬多問題時的誤答）。

**效果（實證）**：`178 + 101=?`、`178+101=?`、`what is 178 + 101=?`、
`178  +  101=?` 全部對齊到 `279`。位置軸從「字串開頭絕對座標」獲得
「**相對錨點的滑動**」自由度 — 這正是先前 §8.1 所述「逐字符一致」限制的
結構性解法。誠實邊界：錨點與空白摺疊是**形式**自由度；`calculate 178 plus
101 = ?` 的 `plus` 是**語義**變異，不在錨點學習範圍（需內容軸/辭典層）。

**自動決策規則**（`prepare_three_axis_datasets.py::decide_plan`）：

每數據集的樣本數 = **min(硬體等級上限, 記憶體預算/單字節成本/平均樣本長度)**。
記憶體是**權威約束**，硬體等級只是上限 — 因為引擎 exact-completions 成本約為
`O(樣本長度²)`，長樣本（alpaca 平均 ~300 位元組）每字節成本 ~18× 高於短樣本
（算術 ~14 位元組）。實測成本（2026-08-19，位元組引擎記憶體記帳）：

| 數據集 | 平均樣本長度 | 每字節成本 | 記憶體預算佔比 |
| --- | --- | --- | --- |
| arithmetic | ~14 位元組 | ~110 B/byte | 15% |
| logic | ~54 位元組 | ~120 B/byte | 25% |
| alpaca | ~300 位元組 | ~2,000 B/byte | 50%（保留 10% 餘裕） |

硬體等級上限（full/medium/small）：

| 數據集 | full | medium | small |
| --- | --- | --- | --- |
| arithmetic | 30,000 | 15,000 | 5,000 |
| logic | 10,000 | 5,000 | 2,000 |
| alpaca | 20,000 | 10,000 | 5,000 |

實測（本機 2 GiB 記憶體上限，HIGH_PERFORMANCE_DESKTOP）：alpaca 記憶體預算
夾到 ~2,000 樣本上下（`min(20000, 1GiB/2000B/300byte)`），實際以 manifest
決策為準、記憶體比例 **0.72**（安全）。決策輸出與理由記錄於 manifest
（`data/checkpoints/three_axis/dataset_manifest.json`）。
